# Case 01: Normal Traffic Baseline

## Scenario

A baseline packet capture was collected from a Windows host using the Wi-Fi interface. The purpose of this capture was to observe normal network behaviour before analysing suspicious traffic in later cases.

## Objective

The objective was to identify common network protocols such as DNS, ICMP, TCP, and TLS, and document how normal traffic appears in Wireshark.

## Lab Environment

- Capture Tool: Wireshark
- Capture Interface: Wi-Fi
- Source Host: Windows host
- Source IP Address: 192.168.10.110
- PCAP File: `pcaps/case01-normal-traffic/case01-normal-traffic.pcapng`
- Total Packets Captured: 1093
- Dropped Packets: 0

## Traffic Generated

- ICMP ping to `8.8.8.8`
- DNS lookup for `example.com`
- Web browsing to `example.com`

## Wireshark Filters Used

| Purpose | Filter |
|---|---|
| DNS traffic | `dns` |
| ICMP traffic | `icmp` |
| TCP traffic | `tcp` |
| TLS traffic | `tls` |
| HTTP traffic | `http` |

## Key Observations

### DNS Traffic

DNS traffic was observed in the capture. The host queried `example.com`, and DNS responses returned IP addresses including `104.20.23.154` and `172.66.147.243`.

Additional DNS queries were also observed for domains such as Google, Grammarly, CurseForge, and GVT-related services. These were likely generated by background applications, browser extensions, or browser-related services.

### ICMP Traffic

ICMP echo request and echo reply traffic was observed between the Windows host and Google DNS.

- Source: `192.168.10.110`
- Destination: `8.8.8.8`
- Activity: ICMP echo request and echo reply

This confirmed basic network connectivity from the host to an external IP address.

### TCP Traffic

TCP traffic was observed throughout the capture. The packets included normal TCP connection behaviour such as SYN, SYN/ACK, ACK, FIN/ACK, and RST/ACK packets.

Several TCP connections used destination port `443`, which is commonly associated with HTTPS traffic.

### TLS Traffic

TLS traffic was observed using TLSv1.2 and TLSv1.3. The capture included TLS handshake packets such as Client Hello and Server Hello, followed by encrypted Application Data.

Some TLS packets showed Server Name Indication values such as Grammarly and CurseForge-related domains. However, the actual application content was encrypted.

### HTTP Traffic

No plaintext HTTP traffic was observed using the `http` filter. This is likely because the browser upgraded the connection to HTTPS or the website redirected to encrypted TLS traffic.

## Conclusion

The capture shows normal baseline network behaviour from a Windows host. DNS queries, ICMP connectivity testing, TCP connection activity, and encrypted TLS communication were observed. No plaintext HTTP traffic was identified, which is expected because modern browsers and websites commonly use HTTPS.

This baseline capture will be used as a comparison point for suspicious traffic in later investigation cases.

## Limitations

This capture was taken from a real Windows host using the Wi-Fi interface. As a result, it includes both intentionally generated traffic and background traffic from applications, browser extensions, and system services.

DNS queries alone should not be treated as proof that a user manually visited a website. They may be caused by background services, preloading, embedded content, or applications running on the host.
