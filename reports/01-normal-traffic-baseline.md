# Case 1 — Normal Traffic Baseline

## Scenario

A baseline packet capture was collected in a controlled three-VM lab to understand normal communication between an internal workstation and an Ubuntu server before investigating suspicious network activity.

The purpose of this case is to identify expected traffic patterns generated by common administrative and service access activities, including ICMP, HTTP, SSH, FTP, and ARP.

## Objective

Establish a clean baseline of normal traffic between the attacker workstation and the victim server.

## Analyst Question

What does normal network communication between the internal workstation and Ubuntu server look like at packet level?

## Capture Command

The packet capture was performed from `analyzer-kali` on the internal lab interface `eth1`.

```bash
sudo tcpdump -i eth1 -nn -w ~/pcaps/01-normal-traffic-baseline.pcap host 192.168.100.30
```

## Traffic Generation Commands

The following commands were executed from `attacker-kali` to generate controlled baseline traffic toward `victim-ubuntu`.

```bash
ping -c 4 192.168.100.30
curl -I http://192.168.100.30
curl http://192.168.100.30
ssh lab@192.168.100.30
ftp 192.168.100.30
```

FTP commands used during the session:

```text

ls

bye
```

## Packet-Level Findings

### Finding 1 — ARP Resolution Was Observed

ARP traffic was observed as part of normal local network communication. The source host resolved the victim server's MAC address before sending IP-based traffic.

This is expected behavior on the internal lab network because hosts need Layer 2 address resolution before they can communicate over IPv4 within the same subnet.

### Finding 2 — ICMP Connectivity Was Successful

ICMP echo request and echo reply packets were observed between `192.168.100.10` and `192.168.100.30`.

This confirms that the attacker workstation could reach the victim server over the internal lab network.

### Finding 3 — HTTP Traffic Was Observed Over TCP Port 80

HTTP traffic was observed between the attacker workstation and the Ubuntu Apache web server. The capture includes HTTP request and response traffic, including successful access to the web service.

The HTTP connection was established using a normal TCP three-way handshake before application-layer HTTP data was exchanged.

### Finding 4 — SSH Traffic Was Observed Over TCP Port 22

SSH traffic was observed between the source host and the victim server over TCP port 22.

The packet capture shows SSH connection metadata and encrypted traffic. Unlike FTP, the SSH password was not visible in plaintext within the packet contents.

### Finding 5 — FTP Traffic Was Observed Over TCP Port 21

FTP control traffic was observed between the source host and the victim server over TCP port 21.

The FTP session showed readable FTP commands, including the lab username and password. This demonstrates that traditional FTP transmits credentials in plaintext.

The credentials used in this case were lab-only test credentials and should not be reused outside this controlled environment.

## MITRE ATT&CK Mapping

No direct MITRE ATT&CK technique is assigned for this baseline case.

This case represents normal expected traffic generation and protocol familiarization rather than suspicious or adversary-like behavior. MITRE ATT&CK mapping will be applied in later investigation cases where activity resembles reconnaissance or command-and-control patterns.

## Conclusion

The baseline capture successfully recorded normal communication between the internal workstation and Ubuntu server. The observed traffic included ARP, ICMP, HTTP, SSH, and FTP.

This baseline provides a reference point for later investigation cases by showing what expected traffic looks like in the controlled lab environment. It also demonstrates important protocol differences, especially between encrypted SSH traffic and plaintext FTP traffic.

## Recommended Actions

* Use this PCAP as the normal baseline reference for later comparisons.
* Retain the capture and screenshots as setup and baseline evidence.
* Avoid using real credentials in plaintext protocols.
* Prefer encrypted alternatives such as SSH/SFTP instead of FTP.
* Continue with separate scenario-specific captures for port scanning, ping sweep activity, DNS investigation, and repeated connection analysis.

## Limitations

This capture was generated in a small controlled lab environment. It does not represent a full enterprise baseline.

The traffic was intentionally generated and therefore does not include normal background noise, multiple users, production services, or external internet activity.

FTP credential exposure was demonstrated using fake lab-only credentials. No real user credentials were used.

Packet capture alone shows network behavior, but additional context such as system logs, process data, authentication logs, and user activity would be needed in a real investigation.
